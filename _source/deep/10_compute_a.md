### EC2 — автопрокат комп'ютерів

**Amazon EC2** («і-сі-ту», Elastic Compute Cloud — еластична обчислювальна хмара) — сервіс оренди **віртуальних серверів**. Кожен окремий сервер називається **інстанс** (instance). Образ з простого курсу — **автопрокат**: обираєш модель, опції й платиш за час.

- Платиш **посекундно** (для Linux і Windows, мінімум — хвилина) або погодинно для деяких систем.
- Повний контроль: будь-яка ОС, будь-які програми — але й відповідальність за ОС і патчі твоя (пам'ятаєш модель спільної відповідальності).
- Інстанс живе в **одній AZ** — у тій підмережі, яку ти обереш.

### Запуск сервера по кроках

Майстер запуску в консолі ставить сім запитань. Тепер ти розумієш кожне:

::: fig ec2-launch | Сім кроків запуску EC2: від імені й образу до ролі й стартового скрипту

1. **Ім'я й теги** — `web-1`, `project = site`.
2. **AMI** — з якого «зліпка» створити сервер: ОС і вже встановлені програми.
3. **Тип інстансу** — скільки vCPU і пам'яті (про типи — нижче).
4. **Key pair** — ключ для входу по SSH. Можна обійтися без нього, якщо заходити через Session Manager.
5. **Мережа** — VPC, **підмережа** (а отже й AZ), чи потрібна публічна IP-адреса, які **Security Groups**.
6. **Сховище** — розмір і тип системного диска EBS.
7. **Додатково** — **IAM-роль** (instance profile, щоб серверу не знадобилися ключі) і **user data** — скрипт, який виконається при першому старті (наприклад, встановить вебсервер).

### AMI — зліпок комп'ютера

**AMI** («ей-ем-ай», Amazon Machine Image) — **шаблон** сервера: операційна система, налаштування й встановлені програми. З одного AMI можна запустити скільки завгодно однакових серверів.

- Бувають AMI від AWS (Amazon Linux, Ubuntu, Windows Server), від сторонніх компаній (AWS Marketplace) і **власні**.
- **Golden AMI** («золотий образ») — власний AMI з уже встановленим і налаштованим застосунком. Новий сервер з нього готовий за хвилину, а не за пів години встановлення — це дуже прискорює масштабування.
- AMI **регіональний**. Щоб запустити такий самий сервер в іншому регіоні (наприклад, для аварійного відновлення), AMI **копіюють** у той регіон.

### Типи інстансів: модельний ряд

Тип — це «модель авто» з певним набором процесора й пам'яті. Сімейства позначають літерами:

| Сімейство | Образ | Для чого |
|---|---|---|
| **T, M** — загального призначення | універсал на щодень | сайти, невеликі бази, більшість задач |
| **C** — compute optimized | спорткар | кодування відео, розрахунки, ігрові сервери |
| **R, X** — memory optimized | вантажівка з великим кузовом | бази й кеші в пам'яті, аналітика |
| **I, D** — storage optimized | авто з величезним швидким багажником | бази з дуже високими IOPS на локальних дисках |
| **P, G, Inf, Trn** — прискорювачі | авто з турбіною (GPU) | машинне навчання, графіка |

**Як читати назву** `m7g.2xlarge`:

::: fig instance-name | Розбираємо назву m7g.2xlarge: сімейство, покоління, особливості, розмір

- **m** — сімейство (загального призначення);
- **7** — покоління (що більше, то новіше й вигідніше);
- **g** — особливість: процесор **Graviton** (ARM, помітно краща ціна за ту саму роботу). Інші літери: **a** — AMD, **i** — Intel, **d** — локальні NVMe-диски, **n** — посилена мережа;
- **2xlarge** — розмір. Розміри йдуть так: `nano`, `micro`, `small`, `medium`, `large`, `xlarge`, `2xlarge`, `4xlarge`… — кожен наступний приблизно **вдвічі** більший.

Сімейство **T** особливе — **burstable** («берстабл», з ривками): сервер зазвичай працює на невелику частку процесора, а в тиху годину накопичує **CPU-кредити**, які витрачає на короткі ривки. Як скарбничка енергії. Ідеально для сайтів, що більшість часу відпочивають.

### Життєвий цикл сервера і гроші

::: fig ec2-lifecycle | Стани інстансу: за обчислення платиш лише в running; у stopped — лише за диски й адреси

- **pending** — готується до старту.
- **running** — працює; **платиш за обчислення**.
- **stopped** — зупинений. За обчислення **не платиш**, але диски EBS і Elastic IP продовжують коштувати. Дані на EBS зберігаються.
- **terminated** — видалений назавжди. Системний диск за замовчуванням видаляється разом із ним.
- **reboot** (перезавантаження) — усе лишається як було, навіть IP.
- **Hibernate** («гайбернейт», сон ноутбука) — вміст оперативної пам'яті зберігається на системний диск (він має бути зашифрований), і після пробудження застосунок продовжує з «теплою» пам'яттю — швидше, ніж холодний старт.

> ⚠️ Звичайна публічна IP-адреса **змінюється** після stop/start. Потрібна постійна — Elastic IP.

### User data, метадані й перевірки стану

- **User data** — скрипт, що виконується при **першому** старті: встановити програми, завантажити налаштування.
- **Instance metadata** — внутрішня «довідка» сервера про себе: його ID, адреси, тимчасові ключі ролі. Безпечна версія — **IMDSv2** (з токенами сесії).
- **Status checks** — AWS постійно перевіряє сервери двома перевірками:
  - **system** — проблема з **фізичним хостом** AWS. Ліки: **stop/start** (сервер переїде на інший хост) або тривога CloudWatch з дією **recover**;
  - **instance** — проблема **всередині** ОС (завис, закінчилася пам'ять). Ліки: перезавантаження, виправлення.

### Мережа сервера

- **ENI** («і-ен-ай», elastic network interface) — мережева карта сервера з приватною адресою. Її можна **перечепити** на інший сервер — і той отримає ту саму приватну адресу (так роблять швидке перемикання на запасний сервер).
- **Elastic IP** — постійна публічна адреса (платна).
- **ENA** — посилена мережа до 100+ Gbps. **EFA** («і-еф-ей», Elastic Fabric Adapter) — надшвидкий зв'язок між серверами для наукових розрахунків (HPC), в обхід операційної системи.

### Placement groups: разом чи окремо

Іноді важливо, **як** фізично розставлені твої сервери. Для цього є **placement groups** («плейсмент груп»):

::: fig placement | Три способи розставити сервери: разом за одним столом, кожен в окремому будинку, секціями з окремими входами

- **Cluster** — **команда за одним столом**: сервери поруч в **одній AZ**, найменша затримка й найвища швидкість обміну між ними. Для HPC (разом з EFA). Ризик: одна «пожежа» зачепить усіх.
- **Spread** — **кожен в окремому будинку**: кожен сервер на окремому обладнанні, щонайбільше **7 серверів на AZ** у групі. Для кількох **критичних** серверів, які не мають зламатися разом.
- **Partition** — **секції з окремими входами**: групи стійок (до 7 секцій на AZ), у кожній — багато серверів. Для великих розподілених систем на кшталт Hadoop, Kafka, Cassandra, які самі розкладають копії по секціях.

### Більший сервер чи більше серверів

- **Вертикально** (більший тип) — сервер треба **зупинити**, змінити тип і запустити. Є межа.
- **Горизонтально** (більше серверів) — без зупинки, через групу автомасштабування. Про це — через розділ.

```lab Запусти свій перший сервер і подивися, як змінюється IP (15 хвилин)
На безкоштовному плані запуск інстансу ще й додає кредити. Головне — наприкінці видалити сервер.

1. У консолі відкрий **EC2** → **Launch instance**.
2. Ім'я: `test-1`. AMI: **Amazon Linux**. Тип: обери такий, що позначений **Free tier eligible**.
3. Key pair: **Proceed without a key pair** — входити по SSH ми не будемо.
4. Network settings: лиши default VPC; зніми галочку, що дозволяє SSH з будь-якої адреси (для цієї вправи вхід не потрібен).
5. **Launch instance**, потім відкрий список інстансів.
6. Подивися на вкладку деталей: **Availability Zone**, **Private IPv4**, **Public IPv4**, тип інстансу, AMI.
7. **Instance state → Stop**. Коли стан стане `stopped`, — **Start**. Порівняй публічну адресу: вона змінилася, а приватна — ні.
8. Прибери за собою: **Instance state → Terminate**.
```

#### 📖 Словничок

- **EC2** («і-сі-ту») — оренда віртуальних серверів; **інстанс** — один сервер.
- **AMI** («ей-ем-ай») — шаблон сервера (ОС + програми); регіональний; **golden AMI** — з готовим застосунком.
- **Тип інстансу** — сімейство + покоління + особливості + розмір (`m7g.2xlarge`).
- **Graviton** — процесори AWS на ARM (літера `g`), краща ціна за роботу.
- **Burstable (T)** — інстанси з CPU-кредитами для коротких ривків.
- **running / stopped / terminated** — працює (платиш) / зупинений (платиш за диски) / видалений.
- **Hibernate** — «сон» зі збереженням пам'яті на зашифрований системний диск.
- **User data** — скрипт першого старту. **IMDSv2** — безпечний доступ до метаданих.
- **System / instance status check** — проблема хоста AWS (stop/start, recover) / проблема ОС (reboot).
- **ENI / Elastic IP / EFA** — мережева карта, яку можна перечепити / постійна публічна IP / надшвидкий зв'язок для HPC.
- **Placement group: cluster / spread / partition** — разом / кожен окремо (7 на AZ) / секціями (до 7 на AZ).

#### ✅ Головне

- **EC2** — «автопрокат» віртуальних серверів з посекундною оплатою; інстанс живе в **одній AZ**.
- Запуск: ім'я → **AMI** → **тип** → ключ → **мережа й SG** → **диск** → **роль** і **user data**. **Golden AMI** прискорює старт; AMI **копіюють** в інший регіон.
- Типи: **T/M** — щоденні, **C** — процесор, **R/X** — пам'ять, **I/D** — швидкі локальні диски, **P/G** — GPU; `g` — **Graviton**.
- **Stopped** — платиш лише за диски й Elastic IP; публічна IP міняється після stop/start; **hibernate** зберігає пам'ять. **System** check → stop/start або recover.
- **Placement**: **cluster** (разом, HPC + EFA), **spread** (окремо, 7 на AZ), **partition** (секціями, Hadoop/Kafka/Cassandra).

### П'ять способів платити

Образ з простого курсу — **транспорт**. Робота та сама, а платити можна дуже по-різному.

::: fig pricing-transport | Способи оплати EC2 як транспорт: таксі, проїзний, горящий тур і власний гараж

### On-Demand — таксі

**On-Demand** («он-діманд», на вимогу) — платиш за секунди чи години роботи, **без жодних зобов'язань**. Увімкнула програма сервер — лічильник пішов, вимкнула — зупинився.

- Найгнучкіше і **найдорожче** за годину.
- Для коротких і непередбачуваних задач, нових застосунків, тестів.

### Savings Plans — проїзний на роки

**Savings Plans** («сейвінгз планз») — ти **зобов'язуєшся витрачати певну суму на годину** (наприклад, 5 доларів) протягом **1 або 3 років**, а AWS дає за це знижку. Два головні види:

- **Compute Savings Plan** — знижка до **~66%** на **будь-яке** сімейство, розмір, регіон і ОС, а також на **Fargate і Lambda**. Можна вільно міняти сервери — знижка «переїде» за тобою.
- **EC2 Instance Savings Plan** — знижка до **~72%**, але прив'язана до **конкретного сімейства в конкретному регіоні** (розмір і ОС міняти можна).

Що більше платиш наперед (без передоплати / частково / повністю) і що довший строк (1 чи 3 роки), то більша знижка.

> 🆕 З грудня 2025 року є ще **Database Savings Plans** — до 35% знижки на бази даних (RDS, Aurora, DynamoDB та інші) за зобов'язання на рік.

### Reserved Instances — лізинг конкретного авто

**Reserved Instances** (RI, «резервд інстансиз») — старший спосіб: бронюєш **конкретний тип** інстансу на 1 або 3 роки.

- **Standard RI** — знижка до ~72%, але змінити сімейство не можна (зате непотрібні RI можна продати на RI Marketplace).
- **Convertible RI** — можна міняти сімейство й ОС, знижка менша.

Savings Plans гнучкіші й сьогодні зазвичай вигідніші для EC2. Але RI досі існують, зокрема для баз даних і кешів. На іспиті обидва варіанти — «довгострокова знижка за постійне навантаження».

### Spot — горящий тур

**Spot Instances** («спот») — AWS продає **вільні потужності**, які зараз простоюють, зі знижкою **до 90%**. Але є умова: коли ці потужності знадобляться іншим, AWS **забере** сервер, попередивши лише **за 2 хвилини**.

Образ — **горящий тур**: дуже дешево, але поїздку можуть скасувати.

::: fig spot | Spot: до 90% дешевше, але AWS може забрати сервер з попередженням за 2 хвилини

Spot ідеальний для задач, які **можна перервати й продовжити**:

- пакетна обробка й нічні звіти;
- рендеринг відео, аналітика великих даних;
- збірка й тестування коду (CI/CD);
- вебсервери **без стану** за балансувальником (впав один — решта працює).

> ⚠️ Spot **не** для основної бази даних і **не** для довгих задач без проміжних збережень (checkpoints) — перервали на 95% роботи, і все спочатку.

Щоб не залежати від одного типу серверів, використовують **Spot Fleet** чи **EC2 Fleet** зі стратегією **price-capacity-optimized** — обирати з кількох типів ті, де вільних потужностей найбільше, а ціна найкраща.

### Dedicated — цілий гараж тільки твій

- **Dedicated Host** («дедікейтед хост») — **цілий фізичний сервер** лише для тебе, і ти **бачиш його сокети й ядра**. Потрібно, коли ліцензії на програми рахуються **за фізичними ядрами** (Windows Server, SQL Server, Oracle — BYOL, «принеси свою ліцензію») або коли цього вимагає регулятор. Найдорожчий варіант.
- **Dedicated Instance** — твої інстанси стоять на обладнанні, яке **не ділиш** з іншими клієнтами, але хостом ти не керуєш і ядер не бачиш.

### Capacity Reservation — бронь місця без знижки

**On-Demand Capacity Reservation** — **гарантія**, що в конкретній AZ для тебе знайдеться потрібна кількість серверів певного типу, на будь-який строк. **Знижки не дає** — лише впевненість (знижку можна додати поверх через Savings Plans). Для важливої події, коли ризикувати не можна.

### Як вибрати: дерево рішень

::: fig pricing-tree | Дерево вибору способу оплати: переривність, постійність, ліцензії, гарантія місця

### Суміш для «Хмаринки»

Реальні системи рідко платять одним способом. Тарас склав таку суміш:

- **Два сервери сайту працюють 24/7 роками** → Compute Savings Plan на 3 роки. Постійна база — постійна знижка.
- **Додаткові сервери у вечірні піки й у Чорну п'ятницю** → On-Demand, який сам додає й прибирає автомасштабування.
- **Нічні звіти** → Spot: якщо сервер заберуть — звіт перезапуститься.
- **Старий бухгалтерський сервер з ліцензією на ядра** → Dedicated Host.
- **Тестові сервери** → вимикати на ночі й вихідні за розкладом.

::: fig pricing-mix | Суміш способів оплати: постійна база — Savings Plans, піки — On-Demand, нічні задачі — Spot

### Ще кілька способів заощадити

- **Правильний розмір** (right-sizing) — не брати «вантажівку» під «пакет з хлібом». Сервіс **Compute Optimizer** підкаже, які сервери завеликі.
- **Graviton** — та сама робота дешевше.
- **Вимикати непотрібне** за розкладом (EventBridge Scheduler — про нього в розділі про черги й події).

#### 📖 Словничок

- **On-Demand** («он-діманд») — «таксі»: без зобов'язань, найдорожче за годину.
- **Savings Plans** — зобов'язання витрачати $/год 1–3 роки. **Compute SP** (до ~66%, будь-що + Fargate і Lambda), **EC2 Instance SP** (до ~72%, сімейство в регіоні).
- **Database Savings Plans** — до 35% на бази даних (1 рік).
- **Reserved Instances** (RI) — бронь конкретного типу на 1–3 роки: Standard (до ~72%) і Convertible.
- **Spot** («спот») — вільні потужності до 90% дешевше; забирають з попередженням за **2 хвилини**.
- **Spot Fleet / EC2 Fleet** — набір Spot і On-Demand з кількох типів; стратегія price-capacity-optimized.
- **Dedicated Host** — цілий фізичний сервер, видно сокети й ядра (BYOL).
- **Dedicated Instance** — обладнання не ділиш з іншими, але хостом не керуєш.
- **Capacity Reservation** — гарантія місця в AZ без знижки.
- **Right-sizing / Compute Optimizer** — правильний розмір / порадник щодо розміру.

### Адміністратор на вході і менеджер зміни

Згадай супермаркет у годину пік:

- **Балансувальник навантаження** (load balancer) — **адміністратор біля входу**: розводить покупців по касах, щоб жодна не була перевантажена, і не посилає людей до зачиненої каси.
- **Автомасштабування** (Auto Scaling) — **менеджер зміни**: черги ростуть — відкриває нові каси, спад — закриває зайві, касир захворів — ставить заміну.

Разом вони дають горизонтальне масштабування, знайоме з розділу про застосунки: не більший сервер, а **більше серверів**.

### Що вміє балансувальник

**Elastic Load Balancing** (ELB) — сімейство балансувальників AWS. Кожен з них:

- дає **одну точку входу** (ім'я в DNS) для всіх серверів;
- розподіляє запити між серверами в **кількох AZ**;
- постійно **перевіряє здоров'я** серверів (health checks): стукає, наприклад, на `/health` і не надсилає запити тим, хто не відповідає;
- може **завершувати HTTPS** на собі (сертифікат ACM), розвантажуючи сервери;
- масштабується сам — керувати ним не треба.

Сервери, між якими балансувальник розподіляє запити, об'єднують у **target group** («таргет груп», цільова група).

### Рівні 3, 4 і 7: образ листа

Балансувальники відрізняються тим, **наскільки глибоко** вони «читають» трафік. Інженери описують це рівнями (з моделі OSI). Уяви лист:

::: fig osi | Рівні трафіку як лист: 3 — адреса на конверті, 4 — номер дверей, 7 — що написано всередині

- **Рівень 3** (мережевий) — **адреса на конверті**: IP-адреси.
- **Рівень 4** (транспортний) — **номер дверей**: протокол TCP чи UDP і порт.
- **Рівень 7** (прикладний) — **зміст листа**: HTTP-запит, шлях `/menu`, домен, заголовки, cookies.

Що вищий рівень, то «розумніші» рішення можна ухвалювати, але й більше роботи на кожен запит.

### Три балансувальники

::: fig lb-types | Три балансувальники: ALB читає, куди тобі треба; NLB — швидкісний турнікет; GWLB — огляд багажу

- **ALB** («ей-ел-бі», Application Load Balancer, **рівень 7**) — адміністратор, що **читає, куди тобі треба**:
  - маршрутизує за **шляхом** (`/api` → одні сервери, `/images` → інші), **доменом** (`api.khmarynka.ua`), заголовками, параметрами, методом;
  - цілі — сервери EC2, IP-адреси, **функції Lambda**, контейнери ECS (з динамічними портами);
  - тримає **кілька сертифікатів** для різних доменів (SNI), вміє **автентифікацію** через Cognito, перенаправляє HTTP на HTTPS;
  - **статичної IP-адреси не має**.
- **NLB** («ен-ел-бі», Network Load Balancer, **рівень 4**) — **швидкісний турнікет**:
  - TCP, UDP, TLS; **мільйони запитів за секунду**, наднизька затримка;
  - **статична IP-адреса в кожній AZ** (можна Elastic IP) — зручно, коли клієнт вносить адресу у свій «білий список»;
  - зберігає справжню IP-адресу клієнта; основа для **PrivateLink**.
- **GWLB** («гейтвей ел-бі», Gateway Load Balancer, **рівень 3**) — **пункт огляду багажу**: прозоро пропускає **весь** трафік через віртуальні апарати сторонніх вендорів — файрволи, системи виявлення вторгнень — і масштабує їх. (Технічно — протокол GENEVE, порт 6081.)
- **CLB** — старий Classic Load Balancer; для нових рішень не обирають.

::: fig alb-routing | ALB маршрутизує за шляхом: /api — на сервери замовлень, /images — на сервери фото

> 🎯 `/api` і `/images` на різні групи серверів → **ALB**. Статичний IP балансувальника → **NLB** (або Global Accelerator). Весь трафік через файрвол вендора → **GWLB**.

### Корисні дрібниці балансувальників

- **Cross-zone load balancing** — розподіляти запити рівномірно між **усіма** серверами в усіх AZ. В ALB увімкнено за замовчуванням і безкоштовно; в NLB і GWLB — вимкнено, а трафік між зонами платний.
- **Deregistration delay** (connection draining) — коли сервер виводять, балансувальник дає йому дообслуговувати поточні запити (за замовчуванням 300 секунд).
- **Sticky sessions** («прилиплі сесії») — завжди відправляти клієнта на той самий сервер. Це **милиця**: правильне рішення — **stateless-сервери**, а сесії — у спільному сховищі (ElastiCache чи DynamoDB). Пам'ятаєш дошку замовлень з розділу про застосунки?
- **Access logs** — журнал усіх запитів до балансувальника в S3.

### Auto Scaling group: менеджер зміни

**Auto Scaling group** (ASG, «ей-ес-джі») — група однакових серверів, кількість яких змінюється автоматично. Налаштування:

- **Launch template** («лонч темплейт», шаблон запуску) — **що** запускати: AMI, тип, Security Groups, роль, user data.
- **Min / desired / max** — не менше ніж, бажано стільки, не більше ніж. Наприклад, 2 / 2 / 10.
- **Кілька AZ** — ASG розкладає сервери по зонах і вирівнює їх.
- **Заміна хворих** — сервер не пройшов перевірку здоров'я → ASG його видаляє й запускає новий.

::: fig asg | Група автомасштабування: мінімум, бажана кількість і максимум у двох AZ за балансувальником

> ⚠️ За замовчуванням ASG перевіряє лише, чи **увімкнений** сервер (статус EC2). Якщо застосунок на сервері **завис**, але сам сервер «живий», ASG нічого не помітить. **Увімкни ELB health checks** в ASG — тоді група дивитиметься на ту саму перевірку, що й балансувальник.

Ще одне налаштування — **health check grace period**: скільки часу після запуску ASG не перевіряє здоров'я, щоб застосунок встиг стартувати. Якщо нові сервери одразу «хворі», бо довго запускаються, — збільш цей період.

### Політики масштабування: як менеджер вирішує

::: fig scaling-policies | Політики масштабування: термостат, розклад, прогноз і сходинки

- **Target tracking** («таргет трекінг») — **термостат**: «тримай середнє завантаження процесора біля 50%» чи «не більше 1 000 запитів на сервер». Найпростіша і рекомендована.
- **Step scaling** — **сходинки**: мале перевищення — додати 1 сервер, велике — додати 4.
- **Simple scaling** — старий спосіб: одна дія і пауза.
- **Scheduled** («шедьюлд») — **за розкладом**: «щопонеділка о 9:00 — 6 серверів», «щоночі — 2».
- **Predictive** («предиктів») — **прогноз**: машинне навчання вивчає історію циклічних піків і додає сервери **заздалегідь**.

Для серверів, що обробляють **чергу завдань**, масштабують за **довжиною черги на один сервер** (backlog per instance) — про черги в розділі про черги й події.

Між масштабуваннями діє пауза (**cooldown**, за замовчуванням 300 секунд) — щоб нові сервери встигли «прогрітися» й менеджер не запанікував.

### Просунуті можливості

- **Lifecycle hooks** («лайфсайкл хукс») — зробити щось перед стартом сервера чи перед його видаленням: встановити програми, **забрати логи**.
- **Warm pools** («ворм пулз») — запас **заздалегідь підготовлених** серверів для застосунків, що довго стартують.
- **Instance refresh** — поступово замінити всі сервери групи на новий AMI **без простою**.
- **Termination policy** — кого прибирати першим при зменшенні (спрощено: з AZ, де серверів найбільше, → зі старим шаблоном → ближчого до нової години оплати).
- **Mixed instances policy** — база з On-Demand плюс Spot, кілька типів серверів.

> 💡 Старий застосунок, що вміє жити лише на **одному** сервері, теж можна зробити самовідновлюваним: **ASG з min = max = 1** плюс ELB health checks. Зламався сервер — група сама поставить новий.

> 🥐 Тепер сайт «Хмаринки» живе за ALB у двох AZ, у групі 2 / 2 / 10 з термостатом «50% процесора» і розкладом «у п'ятницю ввечері — щонайменше 4». Кошики клієнтів лежать не на серверах, а в спільному сховищі. У наступну Чорну п'ятницю група сама виросла до 9 серверів, а до ночі повернулася до двох.

#### 📖 Словничок

- **Load balancer / ELB** — «адміністратор на вході»; сімейство балансувальників AWS.
- **Target group** — група цілей, між якими розподіляють запити.
- **Health check** — перевірка здоров'я цілей (наприклад, `/health`).
- **Рівні 3 / 4 / 7** — IP-адреси / протокол і порт / зміст HTTP.
- **ALB** — рівень 7: маршрути за шляхом, доменом, заголовками; Lambda як ціль; SNI; без статичної IP.
- **NLB** — рівень 4: TCP/UDP, мільйони запитів, статична IP, основа PrivateLink.
- **GWLB** — рівень 3: трафік через апарати безпеки вендорів (GENEVE, 6081).
- **Cross-zone load balancing / deregistration delay / sticky sessions** — рівномірно між зонами / дообслуговування перед виведенням / «прилипання» до сервера.
- **Auto Scaling group, ASG** — група серверів з min / desired / max у кількох AZ.
- **Launch template** — шаблон запуску: AMI, тип, SG, роль, user data.
- **ELB health checks в ASG** — замінювати сервери, чий застосунок не відповідає.
- **Grace period / cooldown** — пауза на старт / пауза між масштабуваннями.
- **Target tracking / step / scheduled / predictive** — термостат / сходинки / розклад / прогноз.
- **Lifecycle hooks / warm pools / instance refresh** — дії при старті й видаленні / прогрітий запас / заміна на новий AMI.

```quiz
? Запити /api і /images мають іти на різні групи серверів. Що обрати?
+ ALB з маршрутизацією за шляхом
- NLB
- GWLB
- Route 53 simple routing
= ALB читає зміст запиту (рівень 7) і вміє розводити за шляхом.
```

#### ✅ Головне

- **Балансувальник** — адміністратор на вході: одна точка входу, кілька AZ, перевірки здоров'я, HTTPS на собі. **ASG** — менеджер зміни: min/desired/max, кілька AZ, заміна хворих.
- Рівні: **3** — адреса на конверті, **4** — номер дверей, **7** — зміст листа.
- **ALB** (7): шлях, домен, заголовки, Lambda, SNI, Cognito; **без статичної IP**. **NLB** (4): TCP/UDP, мільйони запитів, **статична IP**, PrivateLink. **GWLB** (3): апарати безпеки.
- В ASG вмикай **ELB health checks**; довгий старт → **grace period** або **warm pools**; оновлення AMI → **instance refresh**; логи перед видаленням → **lifecycle hook**.
- Політики: **target tracking** (термостат), **scheduled** (розклад), **predictive** (прогноз), **step** (сходинки). Сервери — **stateless**, сесії — у спільному сховищі; старий застосунок — ASG min = max = 1.
