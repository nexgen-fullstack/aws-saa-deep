> 🥐 Настав час будувати «дім» для сайту «Хмаринки» в AWS. «Спершу огородимо ділянку, — каже Тарас, розстеляючи на столі аркуш. — Намалюємо вулиці, квартали, ворота й дорожні знаки. У хмарі це називається VPC. Без неї жоден сервер не має де жити».

### Що таке VPC

**VPC** («ві-пі-сі», Virtual Private Cloud — віртуальна приватна хмара) — це **твоя власна ізольована мережа** в регіоні AWS. Образ з простого курсу — **огороджене містечко** всередині великого міста AWS. Ніхто ззовні не зайде в нього, доки ти власноруч не збудуєш ворота. Сервери, бази й балансувальники «живуть» саме у VPC.

Кілька властивостей:

- VPC — **регіональна**: вона охоплює всі зони доступності регіону;
- в акаунті може бути багато VPC, і за замовчуванням вони **не бачать одна одну**;
- у кожному регіоні вже є **default VPC** — «містечко за замовчуванням» для швидкого старту. Для серйозних проєктів будують власну.

Побудуємо VPC «Хмаринки» за чотири кроки.

### Крок 1. Діапазон адрес — номери будинків

Спершу обирають **CIDR** — діапазон приватних адрес для всього містечка. Ти вже вмієш його читати: `10.0.0.0/16` — це 65 536 адрес.

- Розмір VPC — від `/16` (найбільша) до `/28` (найменша).
- Діапазон варто обирати так, щоб він **не перетинався** з офісом та іншими VPC — інакше їх потім не з'єднаєш.

### Крок 2. Підмережі — квартали в районах

Містечко ділять на **підмережі** (subnets) — квартали. Головне правило: **кожна підмережа живе рівно в одній AZ**. Не може одна підмережа розтягнутися на два райони.

Для надійності кожен вид кварталу роблять **у двох (або трьох) AZ**. Типова схема — шість підмереж:

| Підмережа | AZ a | AZ b | Хто там живе |
|---|---|---|---|
| Публічна | `10.0.1.0/24` | `10.0.2.0/24` | балансувальник, NAT Gateway |
| Приватна — застосунок | `10.0.11.0/24` | `10.0.12.0/24` | сервери з програмою сайту |
| Приватна — бази | `10.0.21.0/24` | `10.0.22.0/24` | бази даних |

У **кожній** підмережі AWS забирає **5 адрес** собі: першу (адреса самої мережі), другу (вбудований роутер VPC), третю (DNS), четверту (запас на майбутнє) і останню. Тому в `/24` для твоїх ресурсів лишається 251 адреса, а не 256.

### Крок 3. Internet Gateway — головні ворота

Щоб містечко спілкувалося з інтернетом, будують **Internet Gateway** («інтернет гейтвей», IGW) — **головні ворота на трасу**. Одна VPC — одні такі ворота. Ними керує AWS: вони самі масштабуються і не бувають «вузьким місцем».

Але самі ворота нічого не вирішують. Щоб машини поїхали до воріт, потрібні вказівники.

### Крок 4. Route tables — дорожні вказівники

**Таблиця маршрутів** (route table) — набір **дорожніх вказівників**: «пакети для таких-то адрес — туди». Кожна підмережа прив'язана до однієї таблиці.

У кожній таблиці завжди є рядок **local**: «усе, що в межах VPC (`10.0.0.0/16`), — всередину». Тому всі квартали одного містечка бачать одне одного.

А тепер найголовніший рядок усього розділу:

| Куди (Destination) | Через (Target) |
|---|---|
| `10.0.0.0/16` | local |
| `0.0.0.0/0` | igw — Internet Gateway |

Рядок `0.0.0.0/0 → igw` означає: «усе, що не наше, — до головних воріт». **Саме він робить підмережу публічною.**

::: fig route-table | Таблиця маршрутів: local — усе всередині VPC; 0.0.0.0/0 → IGW робить підмережу публічною. Перемагає найточніший маршрут

> 💡 Якщо для адреси підходять кілька рядків, перемагає **найточніший** (longest prefix match). Пакет на `10.0.2.5` підходить і під `10.0.0.0/16`, і під `0.0.0.0/0`, але `/16` точніший — тож він піде local, а не в інтернет.

### Публічна чи приватна — вирішує один рядок

- **Публічна підмережа** — у її таблиці є маршрут `0.0.0.0/0 → Internet Gateway`. Ресурси з публічною IP-адресою тут досяжні з інтернету (якщо дозволить охоронець — про охоронців наступний розділ).
- **Приватна підмережа** — такого маршруту **немає**. Ззовні до неї не дістатися в принципі.

У публічних підмережах ставлять лише те, що мусить бути видно назовні: балансувальники, NAT Gateway. Сервери з програмою й бази — у **приватних**.

### Публічні IP і Elastic IP

Щоб ресурс у публічній підмережі був досяжним з інтернету, йому потрібна **публічна IP-адреса**:

- звичайна публічна адреса видається автоматично, але **змінюється**, якщо сервер зупинити й запустити знову;
- **Elastic IP** («еластик ай-пі») — **постійна** публічна адреса, яка належить твоєму акаунту, доки ти її не віддаси. Її можна перечепити на інший сервер.

> 🆕 З 2024 року **всі** публічні IPv4-адреси в AWS платні (погодинно), навіть «вільні» Elastic IP. Тому зайвих публічних адрес не тримають.

### NAT Gateway — виїзд з односторонньою смугою

Сервери в приватних підмережах мусять іноді виходити в інтернет — завантажити оновлення чи звернутися до стороннього сервісу оплати. Але ззовні до них ніхто не повинен дістатися. Пам'ятаєш домашній роутер з розділу про IP-адреси? Тут те саме.

**NAT Gateway** («нат гейтвей») — **виїзд з односторонньою смугою**:

1. NAT Gateway ставлять у **публічну** підмережу (з Elastic IP).
2. У таблиці маршрутів **приватної** підмережі пишуть: `0.0.0.0/0 → NAT Gateway`.
3. Приватні сервери виходять назовні через NAT, а відповіді повертаються тим самим шляхом. Почати з'єднання **ззовні** — неможливо.

::: fig nat-gw | NAT Gateway: приватні сервери виїжджають через односторонню смугу; для надійності — свій NAT у кожній AZ

Що важливо знати для іспиту:

- NAT Gateway — **керований** сервіс: масштабується сам, латати не треба.
- Платиш **за годину роботи і за кожен гігабайт**, що через нього проходить. (Запам'ятай — це повернеться в розділі про гроші.)
- **Для високої доступності — окремий NAT Gateway у кожній AZ**, і приватні підмережі кожної зони ходять через «свій» NAT. Якщо NAT один на всю VPC, то збій його зони відріже інтернет серверам в усіх зонах, а трафік з інших зон до нього ще й коштуватиме грошей (переїзд між районами платний).
- У NAT Gateway **немає** мережевих охоронців (Security Groups).
- Старий самокерований варіант — **NAT instance** (звичайний сервер з вимкненою перевіркою «source/destination check»): дешевший, але без автоматичної надійності й масштабування. На іспиті зазвичай програє NAT Gateway.

> 🆕 З листопада 2025 року є **Regional NAT Gateway** — один NAT на всю VPC, який сам розширюється на потрібні AZ і не потребує публічної підмережі. Але на іспиті частіше питають класичну схему: **NAT у публічній підмережі кожної AZ**.

### IPv6: ворота лише на вихід

В IPv6 кожна адреса публічна, і NAT як такий не потрібен. Але що, як треба дозволити серверам з IPv6 **виходити** в інтернет, не дозволяючи **заходити** до них? Для цього є **Egress-only Internet Gateway** («ігрес-онлі») — **ворота лише на виїзд** для IPv6.

### Увесь малюнок разом

::: fig vpc-full | VPC «Хмаринки»: публічні й приватні підмережі у двох AZ, ворота, NAT у кожній зоні

Простежимо шлях замовлення:

1. Клієнт з інтернету приходить через **Internet Gateway** до **балансувальника** в публічних підмережах.
2. Балансувальник передає запит **серверу застосунку** в приватній підмережі своєї зони.
3. Сервер звертається до **бази** в приватній підмережі баз.
4. Коли серверу треба оновитися, він виходить в інтернет через **NAT Gateway** своєї зони.

Жодна частина не стоїть в одній зоні сама: зламається район A — усе працює в районі B.

```lab Подивися на VPC у консолі й збудуй тренувальну (15 хвилин, безкоштовно)
Сама VPC, підмережі, таблиці маршрутів і Internet Gateway нічого не коштують. Платні лише NAT Gateway, тож у цій вправі ми їх **не створюємо**.

1. У консолі AWS відкрий сервіс **VPC**. Переконайся, що вгорі обрано твій регіон.
2. Розділ **Your VPCs**: знайди default VPC — у неї діапазон `172.31.0.0/16`.
3. Розділ **Subnets**: по одній default-підмережі в кожній AZ. Подивися на колонку Availability Zone.
4. Розділ **Route tables**: відкрий таблицю default VPC — побачиш рядок `0.0.0.0/0` → `igw-…`. Ось чому всі default-підмережі публічні.
5. Тепер натисни **Create VPC** і обери **VPC and more**. Постав: 2 AZ, 2 публічні і 2 приватні підмережі, **NAT gateways: None**, VPC endpoints: None.
6. Праворуч з'явиться **схема-прев'ю**: підмережі, таблиці маршрутів, Internet Gateway — рівно те, що на ілюстрації вище. Натисни **Create VPC**.
7. Порівняй таблиці маршрутів публічних і приватних підмереж: у приватних немає рядка на `igw`.
8. Прибери за собою: **Actions → Delete VPC** для тренувальної VPC.
```

#### 📖 Словничок

- **VPC** («ві-пі-сі») — власна ізольована мережа в регіоні, «огороджене містечко».
- **Default VPC** — готова VPC у кожному регіоні для швидкого старту (`172.31.0.0/16`).
- **Підмережа** (subnet) — «квартал»; живе рівно в одній AZ; AWS резервує 5 адрес.
- **Internet Gateway, IGW** — «головні ворота» VPC в інтернет.
- **Route table** — «дорожні вказівники»; рядок local — усе всередині VPC.
- **Longest prefix match** — перемагає найточніший маршрут.
- **Публічна / приватна підмережа** — є / немає маршруту `0.0.0.0/0 → IGW`.
- **Elastic IP** — постійна публічна IPv4-адреса акаунта (платна).
- **NAT Gateway** — керований «виїзд з односторонньою смугою» для приватних підмереж; платний за годину й гігабайт; для HA — по одному на AZ.
- **NAT instance** — старий самокерований варіант NAT на звичайному сервері.
- **Egress-only Internet Gateway** — ворота «лише на вихід» для IPv6.

#### ✅ Головне

- **VPC** — власне «огороджене містечко» в регіоні: CIDR від `/16` до `/28`, без перетинів з іншими мережами.
- **Підмережа** живе в **одній AZ**; кожен вид підмереж — у 2+ AZ; **5 адрес** у кожній зарезервовано.
- **Internet Gateway** — ворота; **route table** — вказівники; `0.0.0.0/0 → IGW` робить підмережу **публічною**; найточніший маршрут перемагає.
- Балансувальники й NAT — у публічних підмережах; сервери й бази — у **приватних**.
- **NAT Gateway** — вихід назовні без входу ззовні; платний за годину й ГБ; **по одному на AZ**; для IPv6 — **egress-only IGW**. Усі публічні IPv4 (зокрема Elastic IP) платні.

> 🥐 Містечко збудоване, але поки в нього можна постукати звідусіль. Тарас формулює правила: «Клієнти — лише на сайт. До бази — тільки наші сервери. А той набридливий бот з однієї адреси, що сотнями разів на хвилину пробує паролі, — геть назавжди». Для цього в AWS є два охоронці. Вони працюють по-різному, і плутати їх не можна.

### Два охоронці на різних рівнях

- **Security Group** («секьюріті груп», SG) — **охоронець біля дверей конкретного будинку** (сервера, бази, балансувальника). Точніше — біля мережевого інтерфейсу ресурсу.
- **Network ACL** («нетворк ей-сі-ел», NACL, network access control list) — **шлагбаум на в'їзді в квартал** (підмережу). Перевіряє всіх, хто в'їжджає в квартал і виїжджає з нього.

::: fig sg-nacl | Два рівні: шлагбаум NACL на в'їзді в квартал-підмережу і охоронець SG біля дверей кожного будинку

Пакет, що йде ззовні до сервера, проходить **обох**: спершу шлагбаум кварталу, потім охоронця будинку.

### Security Group: охоронець, що пам'ятає

Правила Security Group:

- **лише дозволи** (Allow). **Заборон (Deny) у SG не буває** — усе, що не дозволено, і так заборонено;
- окремо правила на **вхід** (inbound) і на **вихід** (outbound). За замовчуванням вхід — нікому, вихід — усім;
- у правилі вказують **порт** і **джерело**: діапазон адрес (`0.0.0.0/0`, `203.0.113.10/32`) або **іншу Security Group**.

А головне — SG **stateful** («стейтфул», пам'ятає стан). Охоронець **пам'ятає**, хто вийшов з будинку, і сам пускає відповідь назад. Якщо з'єднання дозволене в один бік, відповідь пропускається автоматично — окремих правил для неї не треба.

### Ланцюжок довіри: «пускати всіх з бейджем»

Найкорисніша можливість SG — вказати джерелом **іншу SG**: «пускати всіх, хто носить бейдж охоронної групи вебсерверів». Не треба знати їхні IP-адреси: сервери додаються й зникають, а правило працює.

Для «Хмаринки» це виглядає так:

| Security Group | Вхід дозволено | Звідки |
|---|---|---|
| SG балансувальника | порт 443 (HTTPS) | `0.0.0.0/0` — увесь інтернет |
| SG серверів застосунку | порт 8080 | SG балансувальника |
| SG бази PostgreSQL | порт 5432 | SG серверів застосунку |

::: fig sg-chain | Ланцюжок довіри: інтернет → лише балансувальник; балансувальник → сервери; сервери → база

Зверни увагу: порт 22 (SSH) не відкрито **нікому**. Адміни заходитимуть без нього — як саме, дізнаєшся в наступному розділі.

> 🎯 «База має приймати з'єднання лише від вебсерверів» → **SG бази з джерелом = SG вебсерверів**.

### Network ACL: шлагбаум з пронумерованими правилами

Правила NACL влаштовані інакше:

- є і **дозволи (Allow), і заборони (Deny)**;
- правила **пронумеровані** й перевіряються **від меншого номера до більшого**; спрацьовує **перше збігле**, решта ігнорується;
- наприкінці завжди стоїть правило-зірочка `*`: «усе інше — заборонити»;
- один NACL може обслуговувати кілька підмереж, але в підмережі NACL рівно один. Стандартний (default) NACL пропускає все, а новостворений — нічого, доки не додаси правила.

А головне — NACL **stateless** («стейтлес», не пам'ятає). Шлагбаум перевіряє **кожну машину в обидва боки окремо** і не пам'ятає, що ця ж машина щойно в'їхала. Тому дозволяти треба **і вхід, і відповідь**.

### Ephemeral ports: зворотна адреса відповіді

Щоб зрозуміти, про яку відповідь мова, простежимо один запит.

Клієнт стукає на сайт — на **порт 443**. Але відповідь має повернутися клієнтові не на 443, а на тимчасовий номер «дверей», який його комп'ютер вибрав випадково для цієї розмови, — **ephemeral port** («іфемерал порт», тимчасовий порт), десь у діапазоні **1024–65535**.

::: fig nacl-roundtrip | Один запит і відповідь: SG сам пропускає відповідь, а NACL треба окремо дозволити вихід на тимчасові порти 1024–65535

- **Security Group** запам'ятала з'єднання і сама випустить відповідь.
- **NACL** не пам'ятає нічого: якщо в нього немає правила «вихід на порти 1024–65535 дозволено», відповідь залишиться за шлагбаумом. Сайт «не відповідає», хоча вхід на 443 дозволено.

> ⚠️ Класична пастка: після налаштування NACL сайт «зависає». Найімовірніше, не дозволено **вихід на ephemeral ports 1024–65535**.

### Як заблокувати конкретну адресу

У SG заборон немає, тому заблокувати одну набридливу адресу SG **не може**. Варіанти:

- **NACL з правилом Deny** з номером **меншим**, ніж дозвільні правила (бо спрацьовує перше збігле);
- **AWS WAF** — якщо мова про запити до сайту (рівень HTTP).

Приклад NACL «Хмаринки»:

| № | Тип | Порт | Джерело | Дія |
|---|---|---|---|---|
| 90 | HTTPS | 443 | `198.51.100.23/32` | **DENY** |
| 100 | HTTPS | 443 | `0.0.0.0/0` | ALLOW |
| * | усе | усі | `0.0.0.0/0` | DENY |

Бот з адреси `198.51.100.23` упреться в правило 90. А якби заборона мала номер 200, першим спрацювало б правило 100 — і бот пройшов би.

### Порівняння в одній таблиці

| | Security Group | Network ACL |
|---|---|---|
| Рівень | ресурс (двері будинку) | підмережа (в'їзд у квартал) |
| Пам'ять | **stateful** — відповідь пускає сам | **stateless** — дозволяй обидва боки |
| Правила | лише **Allow** | **Allow і Deny** |
| Порядок | усі правила разом | за **номером**, перше збігле |
| Джерело | адреси або **інша SG** | лише адреси |
| Для чого | основний захист завжди | додатковий шар, блокування адрес |

Мнемоніка з простого курсу: **SG — Stateful, лише Allow. NACL — No memory, Numbered, може Deny.**

#### 📖 Словничок

- **Security Group, SG** («секьюріті груп») — охоронець ресурсу: лише Allow, stateful, джерелом може бути інша SG.
- **Network ACL, NACL** («нейсл», «ей-сі-ел») — шлагбаум підмережі: Allow і Deny, stateless, правила за номером.
- **Stateful / stateless** — пам'ятає з'єднання й сам пускає відповідь / перевіряє кожен напрямок окремо.
- **Inbound / outbound** — правила на вхід / на вихід.
- **Ephemeral ports** («іфемерал портс») — тимчасові порти відповіді, 1024–65535.
- **Правило-зірочка** `*` — останнє правило NACL: «решту заборонити».

#### ✅ Головне

- **SG** — охоронець ресурсу: **stateful**, **лише Allow**, джерелом може бути **інша SG** («ланцюжок довіри»).

- NACL вимагає дозволити **відповідь на ephemeral ports 1024–65535**.
- Заблокувати адресу → **NACL Deny** (або WAF); у SG заборон немає.
- Мнемоніка: **SG — Stateful, лише Allow. NACL — No memory, Numbered, може Deny.**

> 🥐 Сервери «Хмаринки» в приватних підмережах щодня вивантажують сотні фото тортів у сховище S3. Наприкінці місяця Оля бачить у рахунку дивний рядок: «NAT Gateway — обробка даних». «Чому ми платимо за кожен гігабайт, якщо і сервери, і сховище — в AWS?» — «Бо зараз фото їдуть до S3 через NAT, ніби через інтернет, — каже Тарас. — Прокладемо приватну дорогу».

### Проблема: сервіси AWS живуть «за парканом»

Твої сервери живуть у VPC, а багато сервісів AWS — **S3, DynamoDB, SQS, KMS** та інші — живуть **поза нею**, на публічних адресах. Щоб приватний сервер дістався до S3, він за замовчуванням їде через **NAT Gateway** на «загальну трасу».

Це погано з двох причин:

- **гроші** — NAT бере плату за кожен гігабайт;
- **безпека** — трафік виходить з твого огородженого містечка.

Рішення — **VPC endpoints** («ві-пі-сі ендпойнтс»): **приватні дороги** від VPC до сервісів AWS, без інтернету і без NAT.

### Gateway endpoint: безкоштовна дорога до двох складів

**Gateway endpoint** («гейтвей ендпойнт») — найпростіший вид:

- існує лише для **двох** сервісів: **S3 і DynamoDB**;
- **безкоштовний**;
- працює як **новий рядок у таблиці маршрутів**: «до S3 — ось цією приватною дорогою»;
- працює лише для ресурсів **усередині VPC** — з офісу через VPN чи Direct Connect ним скористатися не можна.

Мнемоніка з простого курсу: gateway endpoint — лише «**SD**»: **S**3 і **D**ynamoDB.

::: fig endpoints | Gateway endpoint — безкоштовна дорога в таблиці маршрутів лише до S3 і DynamoDB; interface endpoint — «віконце» з приватною IP-адресою до майже будь-якого сервісу

### Interface endpoint: віконце в стіні містечка

**Interface endpoint** («інтерфейс ендпойнт», технологія **PrivateLink**) — це **мережевий інтерфейс з приватною IP-адресою у твоїй підмережі**, за яким «сидить» потрібний сервіс. Образ — **віконце видачі** просто у твоєму кварталі.

- Існує для **майже всіх** сервісів: SQS, SNS, KMS, Secrets Manager, CloudWatch, ECR, STS і навіть S3.
- **Платний**: за годину в кожній AZ і за гігабайт.
- Доступний і **з офісу** через VPN чи Direct Connect.
- Завдяки «приватному DNS» звичне ім'я сервісу автоматично веде на приватну адресу віконця — код програми міняти не треба.

| | Gateway endpoint | Interface endpoint |
|---|---|---|
| Сервіси | лише S3 і DynamoDB | майже всі |
| Як працює | рядок у таблиці маршрутів | мережевий інтерфейс з приватною IP |
| Ціна | безкоштовно | погодинно + за ГБ |
| З офісу (VPN/DX) | ні | так |

> 🎯 Приватний сервер → S3 або DynamoDB, дешево, без інтернету → **gateway endpoint**. Приватний сервер → SQS, KMS, Secrets Manager → **interface endpoint**. Великий рахунок за NAT через трафік до S3 → **gateway endpoint для S3**.

### Політики endpoint і «лише через мою дорогу»

На endpoint можна почепити **endpoint policy** — обмеження, що можна робити через цю дорогу: наприклад, «лише наші сховища, а не будь-які сховища світу». Це захищає від витоку даних у чуже сховище.

А з іншого боку, у **bucket policy** сховища можна написати: «пускати **лише** через endpoint `vpce-…`» (умова `aws:SourceVpce`) чи «лише з нашої VPC» (`aws:SourceVpc`).

### PrivateLink для власних сервісів

Та сама технологія PrivateLink дозволяє **надати власний сервіс** іншим VPC — навіть в інших акаунтах:

1. **Постачальник** ставить свій сервіс за **балансувальником NLB** і створює **endpoint service**.
2. **Споживач** створює в своїй VPC **interface endpoint** до цього сервісу.
3. Споживач звертається до сервісу через своє «віконце», не заходячи в містечко постачальника.

::: fig privatelink | PrivateLink: сусіди отримують сервіс через віконце у своєму кварталі — не заходячи в чуже містечко

Переваги: доступ **односторонній** (споживач бачить лише сервіс, а не всю мережу), **адреси мереж можуть перетинатися**, і споживачів можуть бути **тисячі**.

> 🎯 «Надати свій сервіс сотням клієнтських VPC приватно, діапазони адрес перетинаються» → **PrivateLink (NLB + endpoint service)**.

### VPC Flow Logs: журнал шлагбаума

**VPC Flow Logs** («флоу логз») — **журнал камер біля шлагбаума**: він записує номери машин і час, але не заглядає в кузов. Технічно — метадані кожного мережевого потоку:

- звідки й куди (адреси й порти), протокол;
- скільки байтів;
- і головне — **ACCEPT** чи **REJECT**: пропустили чи відхилили.

Журнал можна вести для всієї VPC, підмережі чи окремого інтерфейсу й складати в **CloudWatch Logs**, **S3** або **Firehose**. Вміст пакетів Flow Logs **не пишуть** (для цього є окремий сервіс Traffic Mirroring).

Навіщо? Шукати, **чому** не проходить з'єднання (його відхиляє SG чи NACL?), і аналізувати, **хто стукає** в сервери. На Flow Logs, до речі, спирається й GuardDuty.

### Як адміну зайти на приватний сервер

Сервери в приватних підмережах недосяжні ззовні — це добре. Але як тоді адміністраторові полагодити щось усередині?

- **Bastion host** («бастіон», jump box) — класичний спосіб: окремий маленький сервер у **публічній** підмережі з SSH, відкритим лише з адреси офісу. Адмін заходить на бастіон, а з нього — на приватні сервери. Працює, але бастіон треба латати й охороняти, і порт 22 все одно відкритий.
- **SSM Session Manager** («сешн менеджер», з набору Systems Manager) — сучасний спосіб: вхід у консоль сервера **через браузер чи CLI**, **без відкритих портів**, **без бастіону** і **без SSH-ключів**. Хто може заходити — вирішує IAM, а **кожна сесія записується**.
- **EC2 Instance Connect Endpoint** — SSH до приватних серверів без публічних адрес через спеціальний endpoint.

::: fig admin-access | Два шляхи адміна: старий — через бастіон з відкритим портом 22; новий — Session Manager без жодних відкритих портів

> 🎯 «Адмін-доступ до приватних серверів без відкритого порту 22, без бастіону, з записом сесій» → **SSM Session Manager**.

#### 📖 Словничок

- **VPC endpoint** — приватна дорога від VPC до сервісу AWS без інтернету й NAT.
- **Gateway endpoint** — безкоштовний, лише S3 і DynamoDB, рядок у таблиці маршрутів, не з офісу.
- **Interface endpoint / PrivateLink** — мережевий інтерфейс з приватною IP до майже будь-якого сервісу; платний; доступний з офісу.
- **Endpoint policy** — що дозволено робити через endpoint.
- **aws:SourceVpce / aws:SourceVpc** — умови bucket policy «лише через цей endpoint / з цієї VPC».
- **Endpoint service** — власний сервіс за NLB, наданий іншим через PrivateLink.
- **VPC Flow Logs** — журнал метаданих трафіку: хто, куди, ACCEPT чи REJECT.
- **Bastion host** («бастіон») — проміжний сервер для входу адмінів.
- **SSM Session Manager** — вхід на сервер без відкритих портів і ключів, із записом сесій.

- Сервіси AWS живуть поза VPC; щоб не їхати до них через NAT та інтернет, будують **VPC endpoints**.

- **VPC Flow Logs** — хто, куди, ACCEPT/REJECT (без вмісту). Адміни — через **SSM Session Manager** без відкритих портів.
