### Два питання охоронця

На вході в будь-який офісний центр охорона ставить два питання:

1. **«Хто ти?»** — показуєш паспорт чи перепустку. Це **автентифікація** (authentication, «автентикейшн»): перевірка, що ти — це ти.
2. **«Куди тобі можна?»** — охоронець дивиться, які поверхи й кабінети вписано у твою перепустку. Це **авторизація** (authorization, «авторизейшн»): перевірка прав.

Людина може бути автентифікована (охорона знає, хто вона), але не авторизована зайти в серверну. Ці два слова часто плутають — а на іспиті вони мають різні відповіді.

### Пароль і MFA: два замки замість одного

Пароль — це «те, що ти **знаєш**». Його можуть підглянути, вгадати, викрасти через фальшивий сайт.

**MFA** («ем-еф-ей», multi-factor authentication — багатофакторна автентифікація) додає «те, що ти **маєш**»: телефон із застосунком-автентифікатором, що щопівхвилини показує новий код, або фізичний ключ-брелок. Тепер, щоб увійти, треба **і** знати пароль, **і** тримати в руці телефон. Викрадений пароль сам по собі вже нічого не відчинить.

> 💡 Правило, яке варто застосувати з першого дня: MFA — для root і для кожної людини з доступом до консолі.

### IAM — офісний центр із перепустками

**IAM** (читається «ай-ем», Identity and Access Management — керування ідентичністю й доступом) — сервіс AWS, який вирішує, **хто** і **що** може робити в акаунті. Він **глобальний** (один на весь акаунт, а не на регіон) і **безкоштовний**.

Образ з простого курсу — **великий офісний центр**:

- **Root user** — власник будівлі з майстер-ключем. Вмикає MFA, ховає ключ і майже ніколи ним не користується.
- **IAM users** (користувачі) — працівники з особистими перепустками. У кожного — свій логін і пароль для консолі, а для програм — ключі доступу.
- **Groups** (групи) — відділи. Права дають відділу, а працівники отримують їх, бо в ньому числяться. Групи не вкладаються одна в одну: «відділу у відділі» немає.
- **Roles** (ролі) — тимчасові гостьові бейджі, які охорона видає на кілька годин. Власного пароля в ролі немає. Детально — у наступному розділі.
- **Policies** (політики) — **таблички на дверях**: хто, у які двері й за яких умов може заходити.

::: fig iam-office | IAM як офісний центр: власник з майстер-ключем, працівники в групах-відділах, гостьові бейджі й таблички на дверях

### Політика — табличка на дверях

Політика — це невеликий документ у форматі JSON (пам'ятаєш його з розділу про вебсайти?). Ось політика, яка дозволяє читати й завантажувати фото в сховище пекарні:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::khmarynka-photos/*"
    }
  ]
}
```

Розберемо рядок за рядком:

- `"Version": "2012-10-17"` — версія «мови» політик. Завжди саме цей рядок, просто запам'ятай.
- `"Statement"` — список правил. Їх може бути кілька.
- `"Effect"` — **що робити**: `Allow` (дозволити) або `Deny` (заборонити).
- `"Action"` — **які дії**: назва сервісу, двокрапка, назва дії. `s3:GetObject` — «взяти файл із S3», `s3:PutObject` — «покласти файл».
- `"Resource"` — **над чим**: ARN ресурсу. Зірочка `*` означає «будь-що»: `khmarynka-photos/*` — усі файли в сховищі.
- `"Condition"` (необов'язково) — **за яких умов**. Наприклад, лише з адреси офісу або лише якщо людина увійшла з MFA:

```json
"Condition": { "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } }
```

Бачиш знайомий запис `/24`? Це «квартал» адрес офісу з розділу про IP. Усе вивчене раніше тут складається докупи.

Ще одне поле — `"Principal"` (**хто**) — з'являється в політиках, які чіпляють не до людини, а до ресурсу (наприклад, до сховища). Про це — у наступному розділі.

### Як AWS вирішує: три кроки напам'ять

Коли будь-хто робить будь-яку дію, AWS збирає всі політики, що стосуються цього запиту, і перевіряє їх так:

1. **Є явна заборона (`Deny`)?** Якщо хоч в одній політиці написано «заборонити» — **заборонено**. Крапка. Deny перемагає будь-які дозволи.
2. **Є дозвіл (`Allow`)?** Якщо заборони немає, AWS шукає дозвіл. Є — **дозволено**.
3. **Немає нічого?** Тоді **заборонено**. Це «неявна заборона»: за замовчуванням не можна **нічого**.

::: fig iam-decision | Як AWS вирішує: явна заборона → дозвіл → інакше заборонено

Звідси два правила, які розв'язують десятки питань іспиту:

- **Deny б'є все.**
- **Нічого не сказано — значить, не можна.** Новий користувач без політик не може зробити в AWS абсолютно нічого.

(У великих компаніях до цієї перевірки додаються ще «стелі» — правила організації й межі прав. Ми додамо їх у розділі про багато акаунтів, але три кроки лишаються тими самими.)

### Принцип мінімальних прав

**Least privilege** («ліст привілідж») — кожен отримує **рівно ті права, що потрібні для роботи**, і не більше. Марко бачить замовлення, але не видаляє сервери. Соня бачить рахунки, але не чіпає сайт.

Практично це виглядає так:

- починати з нуля прав і додавати потрібне, а не «дати все, потім заберемо»;
- давати права групам, а не кожній людині окремо;
- регулярно прибирати зайве.

Допомагають два інструменти:

- **IAM Access Analyzer** — знаходить ресурси, до яких мають доступ **чужі** акаунти, і вміє згенерувати політику з мінімальними правами на основі того, що людина чи програма справді робила.
- **Access Advisor** («last accessed») — показує, якими сервісами користувач чи роль **реально** користувалися. Рік не заходив в S3 — право на S3 можна забрати.

### Готові й власні політики

- **AWS managed** — готові політики від AWS: `ReadOnlyAccess` (лише дивитися), `AdministratorAccess` (усе), `AmazonS3ReadOnlyAccess` тощо. Зручно, але часто ширше, ніж треба.
- **Customer managed** — власні політики, які ти пишеш і чіпляєш до багатьох груп чи ролей.
- **Inline** — політика, «вшита» в одного конкретного користувача чи роль. Використовують рідко.

За тим, **куди** чіпляють політику, розрізняють:

- **identity-based** — до людини, групи чи ролі: «що **цей хтось** може робити»;
- **resource-based** — до самого ресурсу (сховища, черги, ключа): «**хто** може працювати **зі мною**».

### Ключі доступу: перепустка, що не закінчується

Щоб програма чи командний рядок працювали від імені користувача, йому можна видати **access keys** — пару «Access Key ID + Secret Access Key». Це **довгострокові** облікові дані: вони діють, доки їх не видалять.

Звідси ризик: ключ, що потрапив у код, у спільну папку чи на форум, — як **перепустка, приклеєна скотчем до дверей**. Її знайдуть. Тому для програм, що працюють в AWS, ключі не використовують узагалі — для них є **ролі**. Це тема наступного розділу.

> 🥐 Тарас навів лад: root тепер під MFA і лежить «у сейфі». Створено групи «Адміни» (Тарас), «Замовлення» (Марко) і «Бухгалтерія» (Соня), у кожної — своя політика. Кожен входить у консоль під власним іменем, з MFA. А якщо Марко звільниться, його просто видалять з групи — і ні з ким не доведеться міняти паролі.

#### 📖 Словничок

- **Автентифікація** — перевірка «хто ти». **Авторизація** — перевірка «що тобі можна».
- **MFA** («ем-еф-ей») — другий «замок»: пароль + код з телефона чи ключ-брелок.
- **IAM** («ай-ем») — глобальний безкоштовний сервіс керування доступом.
- **IAM user / group / role** — працівник з перепусткою / відділ / тимчасовий бейдж.
- **Політика** (policy) — JSON-документ: Effect, Action, Resource, Condition (і Principal у політиках ресурсів).
- **Allow / Deny** — дозволити / заборонити. Явний Deny перемагає все.
- **Неявна заборона** — усе, що не дозволено явно, заборонено.
- **Least privilege** («ліст привілідж») — мінімально потрібні права.
- **AWS managed / customer managed / inline policy** — готова від AWS / власна багаторазова / вшита в одного.
- **Identity-based / resource-based policy** — прив'язана до «хто» / до ресурсу.
- **Access keys** — довгострокові ключі для програм і CLI; ризиковані, краще ролі.
- **IAM Access Analyzer / Access Advisor** — пошук зайвого доступу / які сервіси реально використовуються.

#### ✅ Головне

- **Автентифікація** — хто ти; **авторизація** — що тобі можна. **MFA** — другий замок.
- **IAM** — глобальний безкоштовний «офісний центр»: root (майстер-ключ під MFA), users (працівники), groups (відділи), roles (тимчасові бейджі), policies (таблички на дверях).
- Політика: **Effect, Action, Resource, Condition** (+ Principal у політиках ресурсів); `*` — будь-що.
- Перевірка: **явний Deny → Allow → інакше заборонено**. Deny б'є все; нічого не сказано — не можна.
- **Least privilege**: права групам, мінімально потрібні; Access Analyzer і Access Advisor допомагають прибрати зайве. Довгі **access keys** — ризик.

### Чим погані довгі ключі

Ключ доступу (access key) — це перепустка, яка **ніколи не закінчується**. Вона працює, доки хтось не помітить і не видалить її. А помічають зазвичай тоді, коли на рахунку вже з'явилися чужі сервери для майнингу криптовалют.

Потрібна перепустка, яка:

- видається лише тому, кому можна;
- **сама перестає діяти** через короткий час;
- оновлюється автоматично, без людини.

Саме це і є роль.

### Роль — тимчасовий гостьовий бейдж

**Роль** (IAM role) — це набір прав **без власного пароля чи ключів**. Роль ніхто не «має» постійно — її **приймають** (assume, «ассьюм») на певний час.

Коли хтось приймає роль, спеціальна служба AWS — **STS** («ес-ті-ес», Security Token Service — служба токенів безпеки) — видає йому **тимчасові облікові дані**: ключ, секрет і токен, що діють від кількох хвилин до кількох годин. Минув строк — бейдж перетворюється на шматок пластику.

::: fig role-badge | Роль: STS видає тимчасовий бейдж з годинником; строк минув — бейдж більше нічого не відчиняє

Навіть якщо тимчасовий ключ хтось підгляне, користі від нього мало: скоро він стане недійсним.

### Ролі для серверів, функцій і контейнерів

Найчастіше роль приймають не люди, а **сервіси AWS**:

- **EC2** — роль чіпляють до сервера через **instance profile** («інстанс профайл»). Програма на сервері автоматично отримує тимчасові ключі й сама їх оновлює. Образ з простого курсу — **бейдж, прикріплений до робота**: він сам продовжується кожні кілька годин, і нікому не треба ховати ключ.
- **Lambda** — у кожної функції є **execution role** («роль виконання»): що функції дозволено робити.
- **ECS** (контейнери) — **task role**: права саме для конкретного контейнера.

> 🎯 На іспиті: «застосунку на EC2 потрібен доступ до S3» → **IAM role через instance profile**. Варіанти «зберегти ключі в коді», «покласти ключі у файл на сервері» чи «у змінні середовища» — неправильні.

```more Як програма на сервері бачить тимчасові ключі?
Кожен сервер EC2 може звернутися до спеціальної внутрішньої адреси — **сервісу метаданих інстансу** (instance metadata). Там лежать відомості про сам сервер і, якщо до нього прикріплено роль, свіжі тимчасові ключі. Бібліотеки AWS (SDK) самі їх звідти беруть і оновлюють. Безпечна версія цього сервісу — **IMDSv2**: вона вимагає спершу отримати токен сесії, що захищає від деяких хитрих атак. На іспиті іноді питають: «як безпечніше звертатися до метаданих» → IMDSv2.
```

### Дві політики ролі: хто може взяти і що відчиняє

У кожної ролі є дві різні політики:

- **Trust policy** («траст полісі», політика довіри) — **хто може взяти бейдж**: «сервіс EC2», «сервіс Lambda», «користувачі акаунта 111122223333».
- **Permissions policy** (політика дозволів) — **що бейдж відчиняє**: «читати й писати в сховище фото».

::: fig role-two | У ролі дві політики: довіри (хто може прийняти роль) і дозволів (що вона відчиняє)

Ось як виглядає trust policy, що дозволяє серверам EC2 приймати роль:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

`Principal` — **хто**; `sts:AssumeRole` — «прийняти роль».

### Доступ до іншого акаунта

У компанії багато акаунтів, і людям з одного треба часом попрацювати в іншому. Ключі тут теж не потрібні:

1. В **акаунті B** створюють роль, у trust policy якої написано: «довіряю акаунту A».
2. Людина з **акаунта A** (якій її власна політика дозволяє `sts:AssumeRole` на цю роль) «перемикається» в роль.
3. STS видає тимчасові ключі, і людина працює в акаунті B з правами ролі.

::: fig cross-account | Крос-акаунтний доступ: людина з акаунта A приймає роль в акаунті B і отримує тимчасовий бейдж

### ExternalId: захист від «плутанини заступника»

Буває, що доступ до твого акаунта потрібен **сторонній компанії** — наприклад, сервісу, який аналізує рахунки AWS. Ти створюєш для неї роль.

Але уяви: цей сервіс обслуговує тисячі клієнтів. Хитрий клієнт X може вказати сервісу **чужу** роль — твою — і сервіс, сам того не бажаючи, полізе у твій акаунт від імені X. Це називається **confused deputy** («плутанина заступника»).

Захист простий: у trust policy твоєї ролі додають умову **`sts:ExternalId`** — секретну «кодову фразу», яку сервіс видав саме тобі. Без правильної фрази роль не прийняти, а чужу фразу клієнт X не знає.

> 🎯 «Сторонній SaaS-вендор отримує доступ через роль, треба захист від confused deputy» → **trust policy з умовою sts:ExternalId**.

### Resource-based policy: табличка на самому ресурсі

Політику можна причепити не лише до людини чи ролі, а й **до ресурсу**. Найвідоміший приклад — **bucket policy** (політика сховища S3). Інші — політики черг SQS, тем SNS, ключів KMS, функцій Lambda. У таких політиках обов'язково є поле `Principal` — **кому** дозволено.

Наприклад, дозволити акаунту партнера `111122223333` читати файли:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::khmarynka-photos/*"
  }]
}
```

> ⚠️ Для доступу **з іншого акаунта** через політику ресурсу потрібен Allow **з обох боків**: у політиці ресурсу («пускаю акаунт A») **і** в IAM-політиці людини з акаунта A («мені можна туди ходити»). Бракує одного — AccessDenied.

Корисна умова для політик ресурсів — **`aws:PrincipalOrgID`**: «пускати лише акаунти моєї організації», не перелічуючи їх усіх.

### Permission boundary: стеля для конкретної людини

Уяви: розробникам треба дозволити **самим створювати ролі** для своїх програм. Небезпечно: розробник може створити роль з правами адміністратора і взяти її собі.

**Permission boundary** («пермішн баундері», межа прав) — це **стеля** для користувача чи ролі. Навіть якщо політика дає більше, фактичні права — лише те, що вміщується **і** в політику, **і** в межу. Розробникам дозволяють створювати ролі **лише з цією межею** — і вище стелі ніхто не стрибне.

::: fig boundary | Фактичні права — лише перетин: що дозволяє політика І що дозволяє межа

### ABAC: права за ярликами

Замість сотні політик «Марку — ці сервери, Соні — ті» можна написати одну: «людина може керувати ресурсами, у яких тег `project` такий самий, як у неї». Це **ABAC** («ей-бі-ей-сі», attribute-based access control) — доступ за атрибутами (тегами). Новий проєкт — новий тег, а політика та сама.

### Ще кілька інструментів

- **Федерація** — вхід через зовнішню «систему паспортів» (корпоративний каталог, Google) без окремих IAM-користувачів: STS видає тимчасові ключі за підтвердженням від неї (протоколи SAML 2.0 чи OIDC). Детальніше — у наступному розділі.
- **IAM Roles Anywhere** — тимчасові ключі AWS для серверів **поза AWS** (в офісі) за цифровим сертифікатом, без довгих ключів.
- **Credential report** — звіт про всіх користувачів: у кого є пароль, MFA, коли востаннє змінювали ключі.

> 🥐 Тарас видалив злощасний ключ, створив роль «сайт-фото» з правом писати лише в сховище фото й прикріпив її до сервера. Код тепер узагалі не знає жодних ключів. «А якщо сервер зламають?» — питає Оля. «Тоді зловмисник отримає лише право класти фото, і то на годину», — відповідає Тарас.

#### 📖 Словничок

- **Роль** (IAM role) — набір прав без пароля; її тимчасово приймають (assume).
- **STS** («ес-ті-ес») — служба, що видає тимчасові облікові дані.
- **Instance profile** — «кріплення» ролі до сервера EC2.
- **Execution role / task role** — роль функції Lambda / контейнера ECS.
- **IMDSv2** — безпечна версія сервісу метаданих сервера.
- **Trust policy** — хто може прийняти роль. **Permissions policy** — що роль дозволяє.
- **sts:AssumeRole** — дія «прийняти роль».
- **Confused deputy** — «плутанина заступника»; захист — умова **sts:ExternalId**.
- **Resource-based policy** — політика на ресурсі (bucket policy тощо) з полем Principal.
- **aws:PrincipalOrgID** — умова «лише акаунти моєї організації».
- **Permission boundary** — стеля прав для користувача чи ролі.
- **ABAC** («ей-бі-ей-сі») — доступ за тегами.
- **Федерація** — вхід через зовнішню систему ідентичності (SAML, OIDC).
- **IAM Roles Anywhere** — тимчасові ключі для серверів поза AWS за сертифікатом.

#### ✅ Головне

- Довгі **access keys** — перепустка, що не закінчується; для програм в AWS їх замінюють **ролі**.
- Роль приймають на час: **STS** видає **тимчасові** ключі. EC2 — **instance profile**, Lambda — **execution role**, ECS — **task role**.
- У ролі дві політики: **trust** (хто може взяти) і **permissions** (що відчиняє).
- Інший акаунт — роль із довірою; стороння компанія — ще й **sts:ExternalId**. Політика ресурсу (bucket policy) з іншого акаунта — Allow **з обох боків**; «лише моя організація» — **aws:PrincipalOrgID**.
- **Permission boundary** — стеля прав; **ABAC** — доступ за тегами; **Roles Anywhere** — для серверів поза AWS.

### Навіщо багато акаунтів

Один акаунт на все — як одна кімната для всієї компанії: тісно, і будь-яка помилка зачіпає всіх. Окремі акаунти дають:

- **ізоляцію** — помилка чи злам у тестовому акаунті не зачепить робочий сайт (фахівці кажуть «менший радіус ураження», blast radius);
- **окремі права** — розробникам можна все в тестах і майже нічого в робочому акаунті;
- **зрозумілі витрати** — видно, скільки коштує кожен проєкт;
- **окремі ліміти** — квоти одного акаунта не заважають іншому.

### AWS Organizations: головний офіс мережі

**AWS Organizations** — сервіс, що об'єднує багато акаунтів під одним «головним офісом»:

- **Management account** («менеджмент акаунт», керуючий) — головний офіс: створює організацію, запрошує чи створює акаунти, встановлює правила.
- **Member accounts** — філії.
- **OU** («оу-ю», organizational units — організаційні одиниці) — **відділи**, у які групують акаунти: «Робочі», «Тести», «Безпека». OU можна вкладати одна в одну.

::: fig org-tree | Організація: керуючий акаунт, відділи-OU і акаунти-філії; правило SCP діє на всю гілку

Приємний бонус — **consolidated billing** (об'єднаний рахунок): один рахунок за всі акаунти, об'ємні знижки (що більше спожито разом, то дешевше) і спільне використання знижок за довгострокові зобов'язання (до них дійдемо в розділі про оплату серверів).

### SCP: стеля для цілих філій

**SCP** («ес-сі-пі», service control policy — політика контролю сервісів) — правила головного офісу для філій. Їх чіпляють до OU чи акаунта, і вони діють на **всіх** у ньому — навіть на адміністраторів і навіть на root філії.

Головне про SCP — три речі:

1. **SCP — це стеля, а не ключ.** Вона **нічого не дозволяє сама**, лише обмежує максимум. Щоб людина щось могла, їй усе одно потрібен Allow у звичайній IAM-політиці. Але вище стелі SCP не стрибне ніхто.
2. SCP **не діє на management account** — головний офіс правилами для філій себе не обмежує.
3. Типові приклади: «заборонити вимикати журнали CloudTrail», «заборонити працювати поза дозволеними регіонами» (для вимог про дані в ЄС), «заборонити виходити з організації».

Тепер повна перевірка доступу виглядає так — фільтри один за одним:

::: fig policy-layers | Повна перевірка: явний Deny → стеля SCP → межа прав → Allow у політиці → інакше заборонено

- Є явний **Deny** будь-де — заборонено.
- **SCP** організації не дозволяє дію — заборонено.
- **Permission boundary** (якщо є) не дозволяє — заборонено.
- Політика людини чи ресурсу дає **Allow** — дозволено.
- Інакше — заборонено.

> 🆕 З 2024 року є ще **RCP** (resource control policies) — «стеля» для ресурсів в акаунтах організації, наприклад: «до наших сховищ S3 не може звертатися ніхто поза організацією». Є також політики тегів і політики бекапів.

### Control Tower: готова «правильна» організація

Налаштувати організацію за всіма найкращими практиками вручну — довго. **AWS Control Tower** робить це за тебе й будує **landing zone** («лендінг зоун» — «посадкову зону»):

- окремі акаунти для журналів і аудиту;
- централізовані журнали з усіх акаунтів;
- **guardrails** («гардрейлз», огорожі; нині їх звуть controls): **превентивні** (забороняють, через SCP), **детективні** (помічають порушення, через правила AWS Config), **проактивні** (перевіряють шаблони до створення ресурсів);
- **Account Factory** — «фабрика» нових акаунтів, однаково налаштованих з першої хвилини.

> 🎯 «Швидко налаштувати багато акаунтів за найкращими практиками, з огорожами й централізованими журналами» → **Control Tower**.

### Працівники: один вхід в усе — IAM Identity Center

Створювати кожному працівнику окремого IAM-користувача в кожному з двадцяти акаунтів — жах. **IAM Identity Center** (колишня назва — AWS SSO) дає **одну перепустку працівника на всі будівлі компанії**:

- людина входить один раз (single sign-on, «сингл сайн-он») і бачить усі акаунти й бізнес-застосунки, куди їй можна;
- права задають **permission sets** («набори прав»): «адмін у тестах», «лише перегляд у робочому»;
- користувачі можуть жити у вбудованому каталозі Identity Center, у корпоративному **Active Directory** або в зовнішній системі — **Okta**, **Microsoft Entra ID** — через стандарти **SAML 2.0** і **SCIM**.

### Active Directory в AWS: Directory Service

Багато компаній тримають працівників і комп'ютери в **Active Directory** (AD) — корпоративному «довіднику» від Microsoft. **AWS Directory Service** пропонує три варіанти:

- **AWS Managed Microsoft AD** — справжній AD у хмарі; можна налаштувати **довіру (trust)** з AD в офісі.
- **AD Connector** — «перехідник»: запити до офісного AD, нічого не зберігаючи в AWS.
- **Simple AD** — дешевий спрощений сумісний каталог для невеликих середовищ, без довіри з офісним AD.

### Клієнти застосунку: Amazon Cognito

Працівники — це одне, а **клієнти** твого застосунку — зовсім інше: їх тисячі, вони реєструються самі, входять через Google чи Facebook. Для них є **Amazon Cognito** («когніто»). Він має дві частини — і їх постійно плутають:

- **User Pool** («юзер пул», пул користувачів) — **реєстрація і вхід**: email і пароль, вхід через соцмережі чи корпоративні системи, підтвердження пошти, MFA. Після входу видає застосунку **токени** (JWT) — «ти — це пані Ірина». Вміє працювати разом з балансувальником ALB та API Gateway. Це про **хто ти**.
- **Identity Pool** («айдентіті пул») — **тимчасові AWS-ключі** для користувачів застосунку (навіть неавторизованих гостей), щоб застосунок на телефоні міг **напряму** працювати з сервісами AWS — наприклад, завантажити фото в S3. Це про **що тобі можна в AWS**.

::: fig cognito | Cognito: User Pool — вхід і токен «хто ти»; Identity Pool — тимчасові AWS-ключі «що тобі можна»

> ⚠️ Не плутай: **Identity Center** — для **працівників** (вхід в акаунти AWS). **Cognito** — для **клієнтів** твого застосунку. **User Pool** — вхід, **Identity Pool** — ключі до AWS.

### Ділитися ресурсами між акаунтами: RAM

Іноді ресурс зручно створити один раз і дати ним користуватися кільком акаунтам — наприклад, спільну мережу. Для цього є **AWS RAM** («рем», Resource Access Manager): він «ділиться» підмережами (так звана VPC sharing), мережевими хабами, правилами DNS та іншим між акаунтами організації.

### Хто де входить — одна таблиця

| Хто | Куди | Сервіс |
|---|---|---|
| Працівники | в акаунти AWS і бізнес-застосунки | IAM Identity Center |
| Працівники з корпоративним AD | те саме через AD | Identity Center + Directory Service |
| Клієнти застосунку | реєстрація і вхід | Cognito User Pool |
| Клієнти застосунку | напряму до S3, DynamoDB | Cognito Identity Pool |
| Програми в AWS | до інших сервісів | IAM roles |
| Сервери поза AWS | до сервісів AWS | IAM Roles Anywhere |

#### 📖 Словничок

- **AWS Organizations** — об'єднання акаунтів під «головним офісом».
- **Management account / member account** — керуючий акаунт / акаунт-філія.
- **OU** («оу-ю») — організаційна одиниця, «відділ» з акаунтів.
- **Consolidated billing** — один рахунок за всі акаунти й спільні знижки.
- **SCP** («ес-сі-пі») — стеля прав для OU чи акаунта; сама нічого не дозволяє; не діє на management account.
- **RCP** — стеля для ресурсів організації.
- **Control Tower** — готова landing zone з guardrails, журналами й Account Factory.
- **IAM Identity Center** (колишній AWS SSO) — єдиний вхід працівників; permission sets.
- **SAML 2.0 / SCIM** — стандарти входу / синхронізації користувачів із зовнішніх систем.
- **Directory Service** — Managed Microsoft AD, AD Connector, Simple AD.
- **Cognito User Pool** — реєстрація й вхід клієнтів застосунку (токени JWT).
- **Cognito Identity Pool** — тимчасові AWS-ключі для клієнтів застосунку.
- **AWS RAM** («рем») — спільне використання ресурсів між акаунтами.

#### ✅ Головне

- Багато акаунтів = ізоляція, окремі права, зрозумілі витрати. **Organizations**: management account, member accounts, **OU**, **consolidated billing**.
- **SCP** — стеля для OU/акаунтів: **нічого не дозволяє**, лише обмежує; **не діє на management account**. Повна перевірка: Deny → SCP → boundary → Allow → інакше заборонено.
- **Control Tower** — готова landing zone з guardrails і журналами.
- Працівники → **IAM Identity Center** (+ Directory Service для AD). Клієнти → **Cognito**: **User Pool** — вхід, **Identity Pool** — тимчасові ключі до AWS.
- **RAM** — ділитися ресурсами (підмережами, хабами) між акаунтами.
