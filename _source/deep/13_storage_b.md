> 🥐 У «Хмаринки» три нові задачі. База замовлень на сервері гальмує на дешевому диску. Кондитерам у двох цехах потрібна одна спільна папка з рецептами. А бухгалтерія працює на Windows і хоче звичну мережеву папку з входом під корпоративними обліковками. «Три задачі — три різні сховища», — каже Тарас.

### EBS — диск, прикручений до сервера

**Amazon EBS** («і-бі-ес», Elastic Block Store) — блочний диск для серверів EC2. Образ з простого курсу — **жорсткий диск, прикручений до одного комп'ютера** (насправді він мережевий, але працює як власний).

- Диск живе в **одній AZ** — підключити його можна лише до сервера **в тій самій** зоні.
- Зазвичай підключений до **одного** сервера. Виняток — **Multi-Attach** для io1/io2: до 16 серверів у тій самій AZ (для кластерних програм, що вміють ділити диск).
- Диск **живе окремо** від сервера: його можна відчепити й прикрутити до іншого сервера в тій самій AZ. Системний диск за замовчуванням видаляється разом із сервером (прапорець «delete on termination»).
- Шифрування — однією галочкою, а для регіону можна ввімкнути **шифрування за замовчуванням**.

### Типи EBS: від універсала до вантажівки

::: fig ebs-types | Типи EBS як транспорт: універсал gp3, гоночний io2, вантажівка st1, холодний фургон sc1

| Тип | Образ | Для чого | Головні цифри |
|---|---|---|---|
| **gp3** (SSD) | універсал | за замовчуванням: системні диски, більшість застосунків | базово 3 000 IOPS і 125 MiB/s **незалежно від розміру**; до 80 000 IOPS, 2 000 MiB/s, 64 TiB |
| **gp2** (SSD) | старий універсал | старший тип | IOPS залежать від розміру: 3 на GiB, максимум 16 000 |
| **io2 Block Express** (SSD) | гоночний болід | критичні бази | до 256 000 IOPS, 4 000 MiB/s, затримка менша за мілісекунду, Multi-Attach |
| **io1** (SSD) | старий гоночний | старший тип | до 64 000 IOPS |
| **st1** (HDD) | вантажівка | великі послідовні дані: логи, big data | до 500 MiB/s; **не може бути системним** |
| **sc1** (HDD) | холодний фургон | рідко потрібні дані, найдешевше | до 250 MiB/s; **не може бути системним** |

Кілька висновків, які часто трапляються на іспиті:

- **gp3 дешевший за gp2** і дозволяє купити потрібні IOPS окремо від розміру. Перехід gp2 → gp3 робиться **без зупинки** (Elastic Volumes) — і рахунок зменшується.
- Потрібно **понад 80 000 IOPS** на одному диску → **io2 Block Express**.
- HDD-диски (st1, sc1) дешеві, але **не можуть бути системними** і погано працюють з дрібними випадковими операціями.

### Знімки: фотоальбом диска

**Snapshot** («снепшот») — **фотографія** диска на певний момент, яка зберігається в S3 (надійно, у кількох AZ). Знімки **інкрементні**: після першого повного кожен наступний зберігає лише **змінені** блоки — як фотоальбом, куди вклеюють лише нові сторінки.

Що можна робити зі знімками:

- **створити новий диск** з знімка — у **будь-якій AZ** регіону. Так і **переносять диск в іншу зону**: знімок → новий диск там;
- **скопіювати знімок в інший регіон** — для аварійного відновлення чи переїзду;
- автоматизувати: **Data Lifecycle Manager** (DLM) чи **AWS Backup** — «знімок щодня, зберігати 30 днів»;
- **Snapshot Archive** — дешевше для рідко потрібних знімків (відновлення довше);
- **Recycle Bin** — «кошик» для випадково видалених знімків;
- **Fast Snapshot Restore** — новий диск одразу працює на повній швидкості.

::: fig snapshot | Знімок диска: з AZ a в S3 — і вже звідти новий диск в AZ b чи копія в іншому регіоні

**Elastic Volumes** — змінити розмір, тип чи IOPS диска **на ходу**, без зупинки сервера.

### Instance store — крейда на дошці

**Instance store** — диски, фізично вставлені в той самий сервер, на якому працює твій інстанс. **Найшвидші** (найвищі IOPS), але **тимчасові**: дані **зникають**, коли інстанс зупиняють, видаляють або коли ламається фізичний сервер.

Образ з простого курсу — **записи крейдою на дошці**. Лише для кешу, буферів, тимчасових файлів — або коли програма сама тримає копії на кількох серверах.

> ⚠️ Instance store **не переживає stop**. EBS — переживає.

### EFS — спільна мережева папка для Linux

**Amazon EFS** («і-еф-ес», Elastic File System) — керована файлова система **NFS для Linux**. Образ — **спільна шафа з рецептами**, до якої одночасно ходять кондитери з обох цехів.

- Одночасно для **тисяч** серверів EC2, контейнерів (ECS, EKS) і навіть функцій Lambda.
- Працює **в кількох AZ** (є й дешевша One Zone).
- **Росте сама** — від кілобайтів до петабайтів; платиш за використане.
- Класи: **Standard**, **Infrequent Access**, **Archive** — і lifecycle, що сам переносить рідко відкривані файли в дешевші класи.
- Режими швидкості: **Elastic** (рекомендований — підлаштовується сам), Provisioned, Bursting.
- У кожній AZ створюють **mount target** — «точку підключення». Її Security Group має пропускати **NFS, порт 2049** від серверів. Забули — сервери не підключаться (timeout).
- Дорожча за EBS за гігабайт, зате **спільна**.

### FSx — спеціалізовані файлові сервери

**Amazon FSx** («еф-ес-екс») — сімейство керованих файлових систем під особливі задачі:

- **FSx for Windows File Server** — спільні папки для **Windows**: протокол **SMB**, права NTFS, інтеграція з **Active Directory**, кілька AZ. Для бухгалтерії «Хмаринки» — саме воно.
- **FSx for Lustre** («ластер») — **болід Формули-1** для наукових розрахунків, машинного навчання, рендерингу: сотні гігабайтів за секунду, затримка менше мілісекунди, **уміє читати дані прямо з S3** і писати результати назад. Буває тимчасовою (scratch, дешево) чи постійною (persistent).
- **FSx for NetApp ONTAP** — **швейцарський ніж**: NFS, SMB і iSCSI одночасно, Linux, Windows і macOS, знімки, клони, стиснення. Для переїзду з обладнання NetApp.
- **FSx for OpenZFS** — для переїзду з файлових систем ZFS.

::: fig file-options | Яку файлову систему обрати: EFS для Linux, FSx for Windows, FSx for Lustre для HPC, ONTAP — «швейцарський ніж»

#### 📖 Словничок

- **EBS** («і-бі-ес») — блочний диск для EC2; одна AZ; зазвичай один сервер.
- **Multi-Attach** — один io1/io2 диск до кількох серверів в одній AZ.
- **gp3 / gp2 / io2 / io1 / st1 / sc1** — універсал / старий універсал / гоночний / старий гоночний / вантажівка HDD / холодний HDD.
- **Snapshot** («снепшот») — інкрементний знімок диска в S3; з нього — новий диск у будь-якій AZ; можна копіювати в інший регіон.
- **DLM / AWS Backup** — автоматизація знімків.
- **Elastic Volumes** — змінити тип, розмір, IOPS без зупинки.
- **Instance store** — найшвидший, але тимчасовий диск самого фізичного сервера.
- **EFS** («і-еф-ес») — спільна NFS для Linux у кількох AZ; порт 2049; класи з lifecycle.
- **Mount target** — точка підключення EFS у кожній AZ.
- **FSx for Windows / Lustre / NetApp ONTAP / OpenZFS** — SMB з AD / HPC і S3 / NFS+SMB+iSCSI / переїзд з ZFS.

#### ✅ Головне

- **EBS** — диск в **одній AZ**, зазвичай для одного сервера (Multi-Attach — io1/io2). **gp3** — за замовчуванням і дешевший за gp2; **io2 Block Express** — понад 80 000 IOPS; **st1/sc1** — дешеві HDD, не системні.
- **Snapshots** — інкрементні знімки в S3: новий диск у будь-якій AZ, копія в інший регіон; автоматизація — **DLM** чи **AWS Backup**; **Elastic Volumes** — зміни без зупинки.
- **Instance store** — найшвидший, але зникає при stop.
- **EFS** — спільна **NFS для Linux** у кількох AZ, росте сама, порт **2049**, класи з lifecycle.
- **FSx**: **Windows** (SMB + AD), **Lustre** (HPC + S3), **NetApp ONTAP** (NFS + SMB + iSCSI), **OpenZFS**.

> 🥐 «Хмаринка» купила маленьку мережу пекарень у сусідньому місті — разом зі старою серверною. Там сховище NAS на 40 ТБ фото й документів, стара база Oracle, 30 старих серверів і полиця касет з резервними копіями. «Переїжджаємо в AWS, — вирішує Оля. — Але так, щоб пекарні не зупинялися ні на день».

### Жити на два доми: Storage Gateway

Не все можна перенести одразу. Іноді програми в офісі мають і далі працювати зі звичними мережевими папками чи дисками, але дані мають лежати в хмарі. Для цього є **AWS Storage Gateway** («сторидж гейтвей») — **перехідник між офісом і хмарою**. Це віртуальна машина (чи пристрій) в офісі з **локальним кешем**: часто потрібне — під рукою, решта — в AWS.

::: fig storage-gateway | Storage Gateway: в офісі — звичні папки, диски й касети; насправді дані лежать в S3 і Glacier, а часто потрібне — в локальному кеші

- **S3 File Gateway** — звичні **мережеві папки** (NFS, SMB) в офісі, а кожен файл стає **об'єктом у S3** (далі — lifecycle, Glacier, усе, що ти знаєш про S3).
- **Volume Gateway** — **диски iSCSI** для офісних серверів:
  - **Cached** — основні дані в S3, а «гарячі» — в локальному кеші;
  - **Stored** — **усі** дані локально, а в AWS — асинхронні резервні копії (як знімки EBS).
- **Tape Gateway** — **віртуальні касети**: наявні програми резервного копіювання «думають», що пишуть на стрічку, а насправді — в S3 і Glacier. Прощавайте, фізичні касети.

(FSx File Gateway — кеш для FSx for Windows — з жовтня 2024 недоступний новим клієнтам.)

### Скільки їхатимуть 40 терабайтів?

Перш ніж обирати спосіб, треба порахувати. Пам'ятаєш правило «біти ділимо на 8»?

- 40 TB = 40 000 GB = 320 000 гігабітів.
- Канал **100 Mbps** (0,1 Gbps): 320 000 / 0,1 = 3,2 мільйона секунд ≈ **37 днів** — і це якщо канал віддати лише під переїзд.
- Канал **1 Gbps**: ≈ **3,7 дня**.

::: fig transfer-time | Скільки днів їхатимуть 40 ТБ мережею: на повільному каналі — місяць і більше

Орієнтир: якщо передача мережею займе **більше тижня** — розглядай **фізичне** перевезення.

### DataSync — вантажівка по трасі

**AWS DataSync** («дата-синк») — **онлайн**-перенесення й синхронізація великих обсягів **мережею**:

- з офісних сховищ (NFS, SMB, HDFS, інші об'єктні сховища й хмари) — у **S3, EFS, FSx** (і між сервісами AWS);
- ставлять невеликого **агента** в офісі;
- шифрування, **перевірка цілісності**, збереження метаданих і прав доступу;
- **розклад** і обмеження швидкості, щоб не «з'їсти» весь канал у робочий час.

> 🎯 «Перенести 50 ТБ з NAS у S3 мережею, за розкладом, з перевіркою цілісності» → **DataSync**.

### Snowball — контейнер поштою

Коли мережею надто довго чи дорого, дані везуть **фізично**. **AWS Snowball Edge** («сноубол едж») — захищений пристрій-валіза на десятки терабайтів: його привозять, ти записуєш дані, відправляєш назад — і AWS завантажує їх у S3. Образ з простого курсу — **контейнер, який везуть поштою, коли траса надто повільна**. Snowball уміє й обчислювати на місці, де немає нормального інтернету.

> 🆕 З 7 листопада 2025 року Snowball Edge **недоступний новим клієнтам**. AWS радить DataSync, **Data Transfer Terminal** (фізичні точки AWS, куди можна привезти диски й швидко завантажити) або партнерів. Але на іспиті Snowball ще може бути правильною відповіддю: «сотні терабайтів, повільний інтернет, дедлайн — тиждень».

### Transfer Family — вікно для партнерів

Партнери «Хмаринки» надсилають накладні по **SFTP** — і не хочуть нічого змінювати. **AWS Transfer Family** — керований **SFTP / FTPS / FTP / AS2**-сервер, який кладе файли просто в **S3** чи EFS. Партнери працюють як раніше.

### Бази даних: переїзд магазину без зачинення

**AWS DMS** («ді-ем-ес», Database Migration Service) — переносить бази **з мінімальним простоєм**. Образ — **переїзд магазину без зачинення**: товари переносять, а продажі тривають.

1. DMS копіює всі наявні дані з бази-джерела в нову базу.
2. Поки копіює — стара база **працює** як завжди.
3. Далі DMS безперервно доганяє зміни — **CDC** (change data capture, «захоплення змін»).
4. Коли нова база «наздогнала» — застосунок коротко перемикають на неї.

Два випадки:

- **Однаковий рушій** (гомогенна міграція: MySQL → Aurora MySQL, Oracle → RDS Oracle) — вистачить DMS.
- **Різні рушії** (гетерогенна: Oracle → Aurora PostgreSQL, SQL Server → MySQL) — спершу **SCT** («ес-сі-ті», Schema Conversion Tool, або вбудований DMS Schema Conversion) — **перекладач креслень**: перетворює структуру таблиць і код збережених процедур під нову базу. Потім дані везе DMS.

::: fig dms | Переїзд бази без зупинки: SCT перекладає креслення (якщо рушії різні), DMS копіює дані й доганяє зміни

DMS уміє й інші напрямки: у S3, Kinesis, DynamoDB, Redshift. А SCT перекладає ще й сховища даних (наприклад, Teradata → Redshift).

### Сервери: перевезти будинок цілком

- **AWS Application Migration Service** (**MGN**) — «**перевезти будинок цілком**»: фізичні сервери, віртуалки VMware чи Hyper-V, сервери інших хмар **як є** (lift-and-shift) переносять у EC2. MGN безперервно копіює диски, а в день переїзду — коротке перемикання.
- **AWS Elastic Disaster Recovery** (**DRS**) — те саме безперервне копіювання, але як **страховка**: резервна копія офісних серверів в AWS з RPO в секунди й RTO у хвилини.
- **VMware Cloud on AWS** — перенести все середовище VMware без змін інструментів.

### Сім стратегій переїзду: 7 R

Для кожної програми компанія вирішує, **що з нею робити**. Стратегій сім, усі починаються на R. Образ — **переїзд пекарні**:

::: fig seven-r | Сім R: від «викинути стару піч» до «збудувати нову кухню»

1. **Retire** — **викинути**: програма більше не потрібна.
2. **Retain** — **залишити** поки як є (ще не час чи не можна).
3. **Rehost** — **перевезти як є** (lift-and-shift, MGN).
4. **Relocate** — **перевезти разом з фундаментом**: цілий гіпервізор (VMware Cloud on AWS).
5. **Replatform** — **перевезти й трохи підлатати** (lift, tinker and shift): наприклад, базу — на керовану RDS, застосунок — на Beanstalk. Код майже не змінюється.
6. **Repurchase** — **купити готове**: замість старої програми — SaaS.
7. **Refactor / Re-architect** — **перебудувати** під хмару: serverless, мікросервіси. Найдовше, але найбільше користі.

#### 📖 Словничок

- **Storage Gateway** — перехідник офіс ↔ хмара з локальним кешем: File (S3), Volume (Cached / Stored), Tape.
- **DataSync** («дата-синк») — онлайн-перенесення й синхронізація з перевіркою цілісності й розкладом.
- **Snowball Edge** — фізичний пристрій для офлайн-перенесення (новим клієнтам недоступний з листопада 2025).
- **Data Transfer Terminal** — фізичні точки AWS для швидкого завантаження даних.
- **Transfer Family** — керований SFTP/FTPS/FTP/AS2 поверх S3 чи EFS.
- **DMS** («ді-ем-ес») — міграція баз з мінімальним простоєм; **CDC** — безперервне догоняння змін.
- **SCT** («ес-сі-ті») — перетворення схеми й коду бази під інший рушій.
- **Гомогенна / гетерогенна міграція** — той самий рушій / різні рушії.
- **MGN** — перенесення серверів як є (lift-and-shift).
- **Elastic Disaster Recovery (DRS)** — аварійні копії серверів в AWS, RPO секунди.
- **7 R** — Retire, Retain, Rehost, Relocate, Replatform, Repurchase, Refactor.

#### ✅ Головне

- **Storage Gateway** — життя на два доми з локальним кешем: **S3 File** (папки → S3), **Volume** (Cached — основне в хмарі, Stored — усе локально), **Tape** (віртуальні касети).
- Рахуй час: 40 ТБ на 100 Mbps ≈ **37 днів**; довше тижня — фізично. **DataSync** — онлайн з перевіркою; **Snowball Edge** — офлайн (новим клієнтам — Data Transfer Terminal); **Transfer Family** — SFTP для партнерів.
- **DMS** — база без зупинки (CDC); різні рушії → **SCT + DMS**.
- **MGN** — сервери «як є»; **Elastic Disaster Recovery** — аварійні копії серверів; **VMware Cloud on AWS** — переїзд VMware.
- **7 R**: Retire, Retain, **Rehost**, Relocate, **Replatform**, Repurchase, **Refactor**.
